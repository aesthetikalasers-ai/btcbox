# BTCBOX — 当前 AI 协作总指令

**生效日期：** 2026-11-16  
**仓库：** `avali9308-code/btcboxcdt`  
**唯一正式基准：** `main`  
**唯一共同开发分支：** `working`  
**历史备份：** `backup/main-before-unified-replacement-20261107`

> 本文件是 BTCBOX 当前唯一有效的 AI 协作规则。此前旧版协调记录、旧角色分工、旧分支策略及旧任务队列不再具有执行效力。若其他文档与本文件冲突，以本文件为准；业务规则仍以项目所有者在当前对话中的最新明确决定为准。

## 1. 分支与提交规则

1. `main` 是唯一正式基准，所有新任务以最新 `main` 为基础。
2. `working` 是唯一共同开发分支；常规开发、修复和整合统一在此分支进行。
3. `backup/main-before-unified-replacement-20261107` 是历史安全备份，不作为开发分支。
4. 未经所有者明确授权，不创建其他长期分支，不直接推送 `main`，不合并、不发布、不部署。
5. 每次开始工作先核实当前分支、HEAD SHA 和工作区状态；提交时记录变更文件、提交 SHA 和验证结果。
6. 不得覆盖、重置或干扰所有者本地工作区或其他 AI 正在编辑的文件。共享文件先协调，避免并发覆盖。
7. 不得将未经核实的工作描述为已完成、已测试、已上线或已连接。

## 2. AI 职责与协作（双 AI 模式）

当前固定为两位 AI 协作，不设置第三位 AI 或独立协调负责人。

- **AI 1（本助手，后端与整合负责人）：** BTCBOX Wallet 产品/技术架构、API 合约与真实 API 实现、Supabase 数据结构与迁移、钱包账本及业务逻辑、安全与权限、服务端测试、前后端整合和最终技术验收；同时负责维护共同规划、状态和跨 AI 协调记录。
- **AI 2（UI 开发 AI）：** BTCBOX Wallet 视觉蓝图、页面结构、组件、交互、手机/桌面独立适配、响应式和多语言 UI 验收；按本文件及钱包产品规范实现 UI，并通过 API 适配层接入后端。
- **所有者：** 产品决策、业务规则、视觉最终验收、生产数据操作、合并 `main`、生产部署和真实资金操作的最终批准者。

### 钱包产品边界（强制）

BTCBOX Wallet 是独立产品，不是交易所资产页的改名版本。它可以从 BTCBOX Exchange 提供的入口打开，也必须支持独立访问。Wallet 与 Exchange 只共享统一身份认证/账户身份，不默认共用业务资料、资产余额、账本、钱包地址、交易记录或业务数据库。

- 统一认证只证明用户身份；Wallet 和 Exchange 分别维护自己的业务账户、权限、资产和账本。
- 两个系统之间仅通过明确授权、可审计、幂等的 API 执行必要操作，例如用户主动发起的钱包与交易所间转账。
- 交易所不得直接读取钱包私钥或直接写入钱包账本；钱包也不得把交易所余额当作自身余额。
- 钱包页面必须呈现独立产品体验；手机端优先，桌面浏览器端同样完整、美观、可用。不能因嵌入交易所入口而退化为交易所内部通用资产模块。
- 可使用第三方区块链节点、广播、链上数据等底层 API，但最终钱包产品、用户体验、业务 API、账户及账本控制权属于 BTCBOX；密钥生成、保存和签名必须采用经过评估的安全架构，不能把私钥交给普通第三方 API。

### 双 AI 协作规则

1. AI 1 先维护产品边界、API 合约和数据边界；AI 2 按已确认合同并行开发 UI，不必等待所有后端完成。
2. 后端未完成时允许使用明确标记的 Mock 数据，但必须隔离在 API 适配层；不得把 Mock 写死在业务组件中，也不得伪造充值、提现、链上确认或余额变化。
3. 同一文件同一时间只允许一个负责人修改。修改共享文件前先检查分支、HEAD 和工作区状态，避免覆盖另一方工作。
4. 接口必须明确方法、身份来源、请求/响应结构、错误码、权限、幂等规则和真实/未连接状态。
5. AI 1 负责最终前后端整合及技术验收；AI 2 负责 UI 交付与视觉验收证据。双方同步阻塞和接口变更，不设置第三位协调者。

## 3. 登录与注册体验

1. 登录和注册从公开预览/应用页面通过弹窗打开，不采用独立全屏登录注册页面。
2. 顶部 Sign in 打开登录状态，Create account 打开注册状态；同一弹窗内可切换。
3. 关闭弹窗后返回原页面并保留页面上下文。
4. 保留 Supabase Email/Password 与 Google 登录注册能力，不得擅自改成 Google-only。
5. 保留 OAuth callback、session 恢复及正确返回应用的流程。
6. 忘记密码、邮箱验证、密码错误、账号已注册、加载、成功和失败状态必须清楚且本地化。
7. 普通 Email/Google 认证流程不得触发无关 Web3 钱包连接错误，例如 `eth_requestAccounts`。
8. `/login` 和 `/register` 旧地址可兼容，但应进入相应弹窗流程，不应恢复旧式独立全屏页面。
9. 不得以修改 Supabase Provider、密钥或环境配置作为绕过 UI/逻辑问题的捷径。

## 4. Earn 业务规则（所有 AI 必须遵守）

### 活期/灵活收益
- 符合后台已配置条件的资产持有者默认享有活期/灵活收益，无需用户另行申请。
- 活期收益不锁定用户资产。
- 资产资格、收益率、计算频率和发放规则全部以数据库持久化配置为准。

### 定期收益
- 定期产品必须由用户主动选择产品、资产、金额和期限，并明确确认后才能参与。
- 定期收益是在适用活期收益基础上的额外收益，具体按已配置规则计算。
- 不得自动替用户申购定期产品。
- 产品状态、资产、期限、收益率和资格不得硬编码，必须读取后台/数据库配置。

### 钱包和账本
- 余额、可用额、锁定额、本金、收益、到期和发放必须来自真实且一致的服务端/账本状态。
- 金融状态变更必须原子、幂等、可审计；不得直接改显示余额或伪造收益。
- 不得动用用户自持私钥控制的资产。
- 未接通的真实 API 或计算必须明确显示不可用/尚未连接，不得以模拟值冒充真实资金。

## 5. 必须保护的范围

- 保护现有 BTCBOX 品牌与视觉语言，不得擅自整站换模板。
- 保护现有交易页布局及现货、永续、秒合约核心行为，包括行情、K 线、盘口、下单、撤单和钱包集成。
- 未经明确授权，不进行交易页大改、无关大规模重构、认证系统重写或权限系统替换。
- 不进行生产数据库重置、生产数据删除、真实充值提现、真实下单或真实财务入账。
- 不修改 Supabase 项目设置、Auth Provider、密钥、Secrets 或环境变量，除非所有者另行明确授权。

## 6. 视觉与功能验收

固定宽度：**375、390、430、768、1366、1440、1920 px**，并检查断点之间连续变化。

每个受影响页面分别检查手机端、桌面端、全站视觉一致性、连续响应式、文本换行、多语言、加载/空/错误/成功状态、键盘焦点和触控目标。交易页若有改动，必须额外复测关键交易操作。

验收状态只能使用：
- **PASS**：有可复核证据通过。
- **NEEDS FIX**：已发现问题，需修复。
- **NOT VERIFIED**：尚未完成验证或缺少环境条件。

任何关键路径未通过或未验证，不得标记整体最终验收通过。

## 7. 执行与交接

每个任务按以下顺序执行：
1. 核实最新 `main`、`working` 和具体 HEAD SHA。
2. 只检查当前任务必要的代码、API、数据库和配置位置，避免无关全面审计。
3. 明确文件负责人及接口合同。
4. 在 `working` 实施范围明确的变更，避免无关改动。
5. 执行相关构建、类型、单元、接口、认证、数据库或响应式测试。
6. 记录改动文件、commit SHA、测试命令及结果、截图、已知问题和未验证事项。
7. 每次跨 AI 或跨对话交接时更新 `docs/AI_PROJECT_STATE.md`。

新 AI 开始工作必须先阅读：
- `docs/AI_COORDINATION.md`
- `docs/AI_EXECUTION_PLAN_2026-11-16.md`
- `docs/AI_PROJECT_STATE.md`（若已建立）

不得将规划写成已执行事实；不得将本地预览等同于部署；不得将构建通过等同于真实业务链路通过。


## 8. 规划纪律与防止项目漂移（所有 AI，包括本助手）

本节是持续有效的强制规则，不因对话切换、AI 更换、任务增加或阶段交接而失效。

1. **唯一规划来源：** 开始任何 BTCBOX 工作前，重新核对本文件、`docs/AI_EXECUTION_PLAN_2026-11-16.md` 和最新 `docs/AI_PROJECT_STATE.md`。不得凭记忆、旧聊天摘要或个人推测替代仓库中的当前版本。
2. **先定位阶段：** 每次开始任务时，明确当前阶段、该阶段退出条件、当前负责人、已完成证据和下一项具体工作。默认从当前未完成阶段继续，不得无故重启已完成工作或跳到后续阶段。
3. **完成一项再推进：** 每次只推进当前阶段内明确的工作。阶段退出条件未满足时，必须列明缺口并留在该阶段；不得把“已写代码”“本地看起来正常”或“构建通过”当成整个阶段完成。
4. **新需求先归位：** 新提出的需求先判断属于当前阶段、后续阶段还是范围外事项。与当前阶段无关的需求记录到待办，不得擅自插队；若会改变业务规则、阶段顺序、范围、接口或验收标准，先向所有者说明影响并取得明确决定。
5. **禁止规划膨胀：** 不得自行增加平行路线、重复审计、迁移、重建、重命名或额外长期分支。只做当前任务必要的检查和变更，优先完成可交付工作。
6. **每次汇报必须对照规划：** 汇报固定包含：当前阶段与目标、已完成事项及证据、尚未满足的退出条件、当前阻塞、下一步唯一优先任务、是否需要所有者决策。
7. **状态文件是交接事实来源：** 每次阶段完成、负责人变化、重要阻塞或跨对话交接时，更新 `docs/AI_PROJECT_STATE.md`，记录分支和完整 SHA、变更文件、测试结果及未验证事项。不得只在聊天中更新进度而不更新交接状态。
8. **本助手同样受约束：** 本助手不得另起计划、遗忘既定阶段、擅自扩展任务或把建议当成用户决定。每次继续 BTCBOX 工作前，先检查仓库当前规划和状态，并在回复中简要指出当前所处阶段。
9. **冲突处理：** 所有者最新明确决定优先于旧业务讨论；协作规则优先于 AI 自行建议；执行规划决定阶段顺序；项目状态记录实际进度。发现文件互相矛盾时先指出冲突并请求必要决策，不得自行选择有风险的解释。

**每次工作启动提醒：**“先读规则、再看状态、定位阶段、完成当前项、验证退出条件、更新交接；不另起规划、不擅自插队。”


## 9. 统一进度汇报格式（强制）

所有 AI 与开发人员在开始任务、完成任务、遇到阻塞、阶段验收或交接时，必须使用 `docs/AI_STATUS_REPORT_TEMPLATE.md` 的统一格式。汇报必须包含当前阶段、完成事项与文件/分支/完整 SHA、测试命令及可复核证据、未完成事项与阻塞、下一项唯一优先任务，以及规划一致性确认。未验证内容标记 NOT VERIFIED；没有提交不得编造 SHA；阶段退出条件未满足不得报告阶段通过。重要进度和交接同步更新 `docs/AI_PROJECT_STATE.md`。本要求对 AI 1、AI 2 和本助手同样有效。
