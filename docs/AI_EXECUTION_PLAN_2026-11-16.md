在现有 BTCBOX 架构和视觉体系内，完成认证弹窗、Earn 客户端、Admin 配置、后端 API 与 Supabase 钱包/账本基础的真实整合；保护现有交易功能，不以静态演示或模拟数据冒充完成。

- 读取最新 `main` 与 `working` HEAD，记录完整 SHA。

- 仅做任务所需检查，识别必须复用的现有实现和需要保护的文件。

**退出条件：** 明确实际实现入口、文件负责人、接口边界和基线状态。

## 阶段 1：认证弹窗

- 公开预览页的 Sign in / Create account 打开同一弹窗的登录/注册状态。
- 弹窗内可切换，关闭后返回原页面且上下文不丢失。
- 保留 Supabase Email/Password 与 Google 流程、OAuth callback、session 恢复。
- `/login`、`/register` 兼容进入相应弹窗，不恢复旧全屏认证页面。
- 覆盖忘记密码、邮箱验证、账号已注册、无效凭据、加载、成功、失败及本地化。
- 普通认证不应触发无关 Web3 钱包连接或显示 `eth_requestAccounts` 错误。
- 不擅自更改 Provider、密钥、Secrets 或 OAuth 环境配置。

**验证：** 隔离测试账号的 Email 注册/登录、Google OAuth 回调、恢复密码、错误状态、弹窗开关/切换、旧 URL 兼容和无钱包错误。

## 阶段 2：Earn 合同与数据库基础

先统一产品目录、资产、期限、资格、收益率、计算/发放规则、用户持仓、申购、到期、结算、历史记录及 Admin 配置的字段与 API 合同。

数据库必须保证：
- 活期/灵活收益：符合后台配置的持有资产默认享有，无需申请、不锁定资产。
- 定期收益：用户主动选择产品、资产、金额、期限并明确确认；收益按配置在适用活期收益基础上增加。
- 资产资格、收益率、期限、产品状态和发放规则由持久化配置驱动，不硬编码。
- 用户身份从已验证服务端会话取得，不信任客户端传入 user_id 作为授权依据。
- 资金操作原子、幂等、可审计；钱包余额与追加式账本一致。
- 不直接修改显示余额、不插入虚构收益、不动用用户自持私钥资产。
- 使用隔离测试数据，不向生产账本写入。

**交付：** API 合同、迁移/RPC 清单、授权/幂等/余额一致性测试及真实/测试/未连接状态说明。

## 阶段 3：Admin Earn 配置

- 在现有 Admin 架构、导航和 RBAC 内扩展，不建立第二套 Admin。
- 查看、创建、编辑、启用/停用已定义的 Earn 产品参数。
- 查看参与记录、本金、锁定额、收益、到期及发放状态。
- 所有配置必须真实持久化并驱动客户产品目录；操作应有权限验证和审计记录。
- 不添加未经所有者批准的新费率、资产、期限、资格或业务规则。

**退出条件：** 权限受控、配置持久化、客户与 Admin 使用同一数据源。

## 阶段 4：客户 Earn 体验

- 展示真实配置的活期/灵活收益资格与状态。
- 展示可用定期产品及明确的产品、资产、金额、期限和确认步骤。
- 展示真实持仓、可用/锁定金额、累计收益、到期和发放历史。
- 提供加载、空状态、不可用、校验失败和服务错误状态。
- 不把活期默认资格误呈现为用户申购；不因打开页面而自动申购定期。
- 未连接真实 API 时明确显示未连接/不可用，不显示伪造余额、收益或成功状态。

**退出条件：** 客户端所有财务信息来自服务端真实状态或明确标为不可用。

## 阶段 5：端到端账本验证

使用隔离测试身份验证认证、钱包读取、活期资格、收益记账、定期明确申购、余额/锁定变更、重复请求、到期结算、发放及 Admin/客户视图一致性。

核对账本流水、钱包余额、锁定金额、持仓本金、收益和发放之间的对账关系。重复请求不得重复扣款、入账或创建持仓。

**退出条件：** 隔离环境完整链路与账本对账通过；不得使用真实用户资金或生产入账。

## 独立产品工作流：BTCBOX Wallet（与既有阶段并行，双 AI 协作）

本工作流记录所有者于 2026-11-16 明确的产品决定。它不代表功能已实现，也不自动改变上面阶段的既定退出条件；开始执行前仍须按协调规则确认当前优先级与代码基线。

### 产品定位与系统边界

BTCBOX Wallet 是独立钱包产品，可从 BTCBOX Exchange 的钱包入口进入，也可独立访问。按所有者最新决定，建设阶段 Wallet 与 Exchange 暂时共用同一 Supabase 项目/服务器数据库和 Auth，不急于拆库。两者仍是独立产品域，分别维护业务资料、资产账户、余额、账本、地址、交易记录和权限；同库不等于共用资金账本。系统稳定后再规划物理拆分和数据迁移。

- Wallet 维护自己的业务账户、资产、地址、余额、冻结额、账本、充值提现和交易记录。
- Exchange 维护自己的交易所账户、资产账本和交易业务。
- 两边仅通过经过授权、可审计、幂等的 API 进行必要联通；例如用户主动授权的钱包与交易所间转账。
- 不允许交易所直接访问钱包私钥或直接写钱包账本；不允许将交易所余额显示为钱包余额。
- 可接入第三方底层区块链节点、交易广播和链上数据 API，但 BTCBOX 必须拥有自己的产品界面、业务 API、账户与账本控制权。密钥管理和签名必须采用经安全评估的方案，不得把私钥交给普通第三方 API。
- 钱包 API 文档只是接口合同，不代表 API 已实现；Mock、静态页面和配置好的固定充值地址都不能冒充真实钱包能力。

### AI 1 — 后端、架构与整合

- 维护独立钱包服务边界、认证映射和 API 合约。
- 实现真实的钱包总览、资产、地址、账本、充值、提现和授权转账接口；每项按真实能力分阶段交付。
- 评估并接入底层第三方区块链服务，处理地址、链上监听、确认、广播与 Webhook；对服务商能力和未接通状态如实标记。
- 保证服务端身份验证、授权、幂等、金额精度、账本一致性、审计和密钥安全。
- 负责 Supabase/后端整合、接口测试、前后端联调和最终技术验收。
- 不擅自修改生产配置、执行真实资金操作或部署生产环境。

### AI 2 — UI 与体验

- 先提交钱包视觉蓝图和页面信息架构，再按模块实现；无需等待所有后端 API 完成。
- 页面至少覆盖：钱包首页/资产总览、币种详情、充值、提现、钱包与交易所转账、交易记录与详情、地址管理、安全设置。
- 完整实现加载、空数据、错误、成功、确认、未连接/不可用等状态；不伪造链上成功、到账或余额变化。
- 手机端优先，同时保证桌面浏览器端完整、美观、易用；统一设计语言但允许按设备独立优化。
- Mock 仅用于 UI 开发，必须经独立 API 适配层注入并明确标记；真实接口就绪后可替换，不得将模拟数据写死在业务组件。
- 按 BTCBOX 视觉规范测试 375、390、430、768、1366、1440、1920 px，并检查断点之间连续变化及多语言排版。
