# BTCBOX — 全项目专业交易终端升级执行指令

你现在负责 BTCBOX 项目的全栈开发、专业交易终端 UI/UX、业务整合与质量验收。

本任务不是制作独立 Demo、静态页面或只提供建议。你必须基于当前本地 BTCBOX 完整源码，结合本包 `reference/trading-terminal/` 中的六个参考文件，实际开发、整合、修复和测试。

## 0. 执行原则（最高优先级）

- 当前本地 BTCBOX 源码是唯一工程事实来源；参考文件仅作为视觉与技术思路，不是要求直接覆盖正式项目文件。
- 不要重新创建项目，不要另起一套孤立前端。
- 不要只输出审计报告；完成必要理解后立即开始开发。
- 批量推进已授权的安全工作，不要每改一个文件就停下来询问。
- 保护用户已有未提交修改、交易核心逻辑、认证、数据库、API 和生产环境。
- 不得伪造真实行情、持仓、订单或下单成功。
- 不得擅自执行真实资金交易、生产数据库写入、生产部署、合并主分支或推送代码。
- 遇到缺少密钥、权限或外部服务时，完成不依赖该条件的工作，并准确记录阻塞项。

## 1. 开始前：项目与 Git 保护

1. 确认当前工作目录是 BTCBOX 项目根目录。
2. 读取 Git 分支、`git status`、未提交差异和最近提交。
3. 不得丢弃、覆盖或重置用户已有修改。
4. 如需隔离开发，使用独立分支；不要擅自改写历史。
5. 检查项目实际 Next.js、React、TypeScript、Tailwind 版本和 package scripts。
6. 不要为了适配参考文件而盲目替换 `package.json`、Tailwind 配置、全局 CSS 或页面入口。

## 2. 必要范围理解

检查并定位：
- App Router / Pages Router 与实际页面入口
- 交易页面、布局、组件及样式
- 现有行情数据源、WebSocket、REST API
- K 线、深度图及图表库
- 下单、撤单、订单状态、持仓与资产接口
- Supabase schema、RLS、认证和服务端访问方式
- Email/Password、Google、钱包登录现状
- 多语言配置、翻译文件与语言切换机制
- 现有测试、构建、部署配置
- 手机端与桌面端布局

只做当前开发所必需的检查，不要陷入无止境的全面审计。将关键发现记录后继续实施。

## 3. 设计目标

以参考文件的专业深色交易终端方向为基础，结合 BTCBOX 品牌与现有设计系统，提升真实交易页面：

- 精致、克制、现代、专业的金融终端视觉
- 清晰的信息层级、字体、数字排版、对齐和间距
- 统一背景、表面、边框、状态色、圆角和交互反馈
- 合理的信息密度，避免拥挤、空洞和无意义装饰
- 卡片尺寸根据内容和屏幕空间合理变化，不强求所有卡片等大
- 兼顾可访问性、键盘操作、焦点态和触控尺寸

不要简单复制 Binance 的品牌标识、布局细节或视觉资产。不要加入未经要求的品牌仿制元素。

## 4. 交易页面布局

保护既有交易操作关系和业务流程；在不破坏功能的前提下优化比例、尺寸和布局。

桌面端目标分区：
- 左侧：盘口、买卖深度数据、最新成交
- 中间：K 线、周期切换、必要指标、深度图
- 右侧：限价/市价等现有订单类型、价格、数量、可用余额、比例选择、买卖操作及风险信息
- 底部：持仓、当前委托、历史订单、成交记录、资产

不得删除 BTCBOX 现有且仍有效的交易功能。不得把现货、合约、理财、期货混为一谈。每种业务必须沿用各自真实规则、接口和数据类型。

## 5. 手机端独立设计

手机端不是桌面布局的缩小版。重新组织信息优先级和操作路径：
- 行情摘要优先展示
- 盘口与成交采用适合窄屏的切换或紧凑结构
- K 线保留足够可视面积
- 下单入口和关键操作容易触达
- 持仓、委托、历史数据适配窄屏
- 输入框、键盘、弹窗和底部操作不互相遮挡
- 不得出现页面级横向溢出、内容裁切或按钮不可达

## 6. 行情与盘口真实性

先确认 BTCBOX 当前行情数据源和业务设计，不得默认把示例 Binance 现货 WebSocket 用作全部市场的数据源。

如需实现或修复 order book：
- 正确获取初始快照
- 正确应用增量更新及序列号/事件连续性校验
- 正确维护买卖档位、排序、数量为零时删除
- 断线自动重连、退避和重新同步
- 防止重复订阅、过期回调和卸载后更新
- 处理无效数据、网络错误和连接状态
- 只展示真实接收的数据；连接失败时明确显示状态

现货与合约必须使用正确且独立的数据源、交易对映射和规则。不要把示例代码中的静态价格或模拟盘口当作真实数据。

## 7. K 线与图表

检查现有图表实现并优先复用。若不存在，选择与项目现有依赖兼容的方案。确保：
- 数据来源真实且交易市场正确
- 周期切换有效
- 时间、价格、成交量映射正确
- 实时更新机制可靠
- 加载、空数据、错误和断线状态明确
- 手机端可操作、可读
- 不使用占位文字冒充图表已实现

如涉及 TradingView，先确认项目已有授权、库文件和可用接入方式；不得声称已接入未实际存在的 Charting Library。

## 8. 下单、撤单和订单管理

必须沿用现有真实业务接口和服务端权限边界。检查：
- 限价、市价及现有订单类型
- 输入格式、价格/数量精度
- 最小下单量、最小名义金额
- 余额与风险校验
- 防重复提交
- 提交中、成功、失败反馈
- 订单状态同步
- 撤单权限及结果反馈
- 持仓、委托、成交和资产数据来源

不得只实现按钮外观。不得绕过服务端风控、RLS 或权限检查。不得把成功提示写死。没有真实交易接口时，将功能标记为未完成，不得伪造成功，也不得在测试中发起真实资金订单。

## 9. 认证、Supabase 与数据保护

- 保留现有 Email/Password、Google 和钱包登录能力及其真实实现。
- 不得擅自更换认证体系或破坏用户会话。
- 不得把 Supabase Service Role Key 或任何秘密暴露到客户端。
- 数据库变更必须有明确必要性；优先兼容现有 schema。
- 如确实需要变更，生成可审查迁移文件，说明影响和回滚方式。
- 不删除表、字段、用户或交易数据。
- 不直接写入生产数据库。
- 保留现有用户 ID 规则和身份映射，不擅自更改递增规则。

## 10. 全站一致性与多语言

交易页面升级不得造成全站视觉系统割裂。检查并按需统一首页、登录注册、现货、合约、理财、期货、账户、资产、订单、用户中心、设置、弹窗、通知和空状态。

保留现有多语言机制及当前规划的七种语言。所有 UI 文案必须通过翻译机制，不得在组件中硬编码单一语言。检查：
- 标题、导航、按钮、输入提示
- 校验、成功、失败和通知消息
- 订单、持仓、交易状态
- 表格、弹窗、空状态
- 长文本、数字格式和手机端换行

语言切换后所有相关文本必须同步更新，不得溢出、挤压或破坏布局。
